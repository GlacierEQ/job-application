# Portfolio Proof Repository Coverage Contract

## Purpose

Portfolio-proof compilation must consider the **full authenticated engineering estate**, then project only the strongest evidence-bounded canonical systems. The admitted 67-repository public portfolio is a presentation boundary, not the search boundary for capability discovery.

This prevents two opposite errors:

1. omitting a relevant engineering repository merely because it is outside the admitted public subset; and
2. inflating repository count by treating forks, backups, archives, support ancestry, or successor copies as independent accomplishments.

## Governing inclusion rule

For every proof cycle:

1. Start from the authenticated owned-estate graph when available.
2. Apply namespace isolation and fork/reference exclusion.
3. Collapse only evidence-supported lineage into canonical systems.
4. Evaluate **every independent canonical engineering system** for relevance to the selected capability, role, company bottleneck, or claim under audit.
5. Include all materially relevant independent donors in the internal proof map.
6. Use a bounded public set-cover projection so recruiter surfaces remain concise.
7. Preserve omitted relevant donors as machine/mesh support evidence rather than pretending they do not exist.
8. Never count support/reference relationships, forks, backups, archives, experiments, or lineage siblings as additional accomplishments.
9. Keep evidence level explicit: source-contract evidence is not runtime-test or deployment evidence.
10. Re-run coverage whenever the estate census, lineage facts, repository head, capability registry, or target role/company changes.

## Projection rule

A recruiter surface does not need to enumerate every donor. It should select the smallest set of independent canonical systems that proves the capability without redundancy. Master, machine, and mesh surfaces should retain the fuller donor graph and explain why any excluded repository is lineage/support/reference-only or materially redundant.

## Coverage invariant

> A capability proof is incomplete if a materially relevant independent canonical system exists in the current estate but is omitted merely because it falls outside the admitted public inventory or was not part of an earlier manual donor list.

The inverse is equally binding:

> A repository must not be added as an independent donor when its value is only fork/reference ancestry, backup/archive lineage, successor duplication, dependency support, or unverified similarity.
