# Helix Repository Excellence Compiler — Recruiter / Master / Machine / Mesh

**Proof ceiling:** implementation-inspected control-plane capability. This surface does not claim current exact-head repository-native test execution, autonomous estate-wide enforcement, production deployment, or universal repository equivalence.

## Recruiter

Built a repository-evolution control plane that refuses to treat polished documentation as completion. Repositories move through explicit lifecycle states only when machine-verifiable evidence supports the next gate, while blocked, experimental, superseded, retirement-ready, and quarantined paths remain first-class outcomes instead of being hidden as failure noise.

The current Helix implementation separates intended architecture, current proof strength, company fit, and canonical confidence rather than collapsing them into one vanity score. That makes unfinished systems legible without weakening the target architecture or inflating current capability.

## Master

The compiler implements a monotonic repository lifecycle:

`DISCOVERED → IDENTITY_RESOLVED → PROBLEM_VERIFIED → TARGET_CONTRACTED → SEEDED → VERTICAL_SLICE → IMPLEMENTED → TESTED → ADVERSARIAL_VERIFIED → OPERABLE → PROOF_REPRODUCED → PROMOTED → CANONICAL → EVOLVING`

with explicit side exits:

`BLOCKED | EXPERIMENT | REFERENCE | SUPERSEDED | RETIREMENT_READY | QUARANTINE`

The inspected implementation enforces several important boundaries:

- principal transitions advance exactly one state at a time;
- side exits are explicit and recover only through a defined route;
- `PROOF_REPRODUCED → PROMOTED` requires security/authority and projection-consistency gates;
- `CANONICAL` and `EVOLVING` require resolved canonical identity;
- repository excellence is conjunctive across problem, lineage, implementation, deterministic proof, adversarial proof, runtime observation, security/authority, SHA-bound receipts, capability extraction, truth-consistent projections, and an evolution cursor;
- architecture target, proof grade, company fit, and canonical confidence remain independent axes.

This turns repository maintenance into a governed promotion system rather than a documentation exercise or repository-count metric.
